O que é Spring Boot e por que usamos

Framework · Autoconfiguração · Servidor Embutido

Spring Boot É um framework Java que simplifica a criação de aplicações web e APIs REST. Ele elimina a necessidade de configuração manual XML, já vem com um servidor web embutido (Tomcat) e configura automaticamente tudo que detecta no classpath.

Por que Spring Boot e não Spring puro?

Spring puro (antigo)

  • Precisava configurar tudo manualmente em XML
  • Configurar o servidor separadamente (Tomcat, JBoss)
  • Centenas de linhas de configuração para um projeto simples
  • Alta curva de aprendizado

Spring Boot (atual)

  • Autoconfiguração inteligente
  • Servidor Tomcat embutido (roda com java -jar)
  • Starters que agrupam dependências por funcionalidade
  • Projeto funcionando em minutos

Starters usados neste projeto

StarterO que inclui automaticamente
spring-boot-starter-webTomcat embutido + Jackson (JSON) + Spring MVC
spring-boot-starter-data-jpaHibernate + Spring Data + gerenciamento de transações
spring-boot-starter-validationHibernate Validator (Bean Validation)
spring-cloud-starter-openfeignCliente HTTP declarativo para APIs externas
springdoc-openapi-starter-webmvc-uiSwagger UI + documentação automática
spring-security-cryptoBCrypt para hash de senhas (sem ativar segurança completa)

A anotação mais importante: @SpringBootApplication

@SpringBootApplication  // junta 3 anotações:
public class TechbackApplication {
    public static void main(String[] args) {
        SpringApplication.run(TechbackApplication.class, args);
    }
}
// @SpringBootApplication = @Configuration + @EnableAutoConfiguration + @ComponentScan
O Spring Boot escaneia todos os pacotes a partir do pacote da classe principal e registra automaticamente todos os beans (@Component, @Service, @Repository, @Controller etc).

Arquitetura em Camadas (MVC)

Controller → Service → Repository → Banco de Dados

Arquitetura em Camadas É um padrão de organização do código onde cada camada tem uma responsabilidade específica. Uma camada só se comunica com a camada imediatamente abaixo. Isso torna o código mais organizado, testável e fácil de manter.

Entidades JPA — O Modelo de Dados

@Entity · @Table · @Id · @ManyToOne · @CreationTimestamp

JPA (Java Persistence API) É uma especificação Java que define como objetos Java são mapeados para tabelas de banco de dados. O Hibernate é a implementação mais usada do JPA. Com JPA, você escreve classes Java e o Hibernate cria e gerencia as tabelas automaticamente.

Anotações de Entidade — Explicadas

AnotaçãoOnde ficaO que faz
@EntityNa classeDiz ao Hibernate que esta classe representa uma tabela no banco
@Table(name="...")Na classeDefine o nome da tabela. Sem ela, usa o nome da classe
@IdNo campo idMarca este campo como chave primária (PRIMARY KEY)
@GeneratedValue(strategy = IDENTITY)No campo idO banco gera o ID automaticamente (AUTO_INCREMENT)
@Column(unique=true)No campoCria constraint UNIQUE no banco
@Column(nullable=false)No campoCria constraint NOT NULL no banco
@Column(columnDefinition="TEXT")No campoDefine o tipo da coluna como TEXT (para textos longos)
@ManyToOneNo campoRelacionamento N:1 — muitos registros apontam para um
@JoinColumn(name="...")No campoDefine o nome da coluna de chave estrangeira (FK) no banco
@CreationTimestampNo campoHibernate preenche automaticamente com a data/hora atual ao criar

Exemplo completo: Entidade Usuario

@Data @Builder @NoArgsConstructor @AllArgsConstructor  // Lombok
@Entity                                              // marca como tabela
@Table(name = "usuarios")                          // nome da tabela no banco
public class Usuario {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;                                  // chave primária auto

    @NotBlank
    private String nome;

    @Email @NotBlank
    @Column(unique = true)                           // e-mail único no banco
    private String email;

    private String senhaHash;                         // senha já criptografada

    @Past
    private LocalDate dataNascimento;                 // deve ser data passada

    @CreationTimestamp
    private LocalDateTime criadoEm;                   // preenchido automaticamente
}

Relacionamentos: Entidade Assinatura

Repositórios — Spring Data JPA

JpaRepository · @Query · JPQL · Derived Queries

Spring Data JPA É uma camada sobre o JPA que elimina a necessidade de escrever código JDBC ou queries SQL para operações básicas. Ao criar uma interface que extende JpaRepository<Entidade, TipoDoId>, o Spring cria automaticamente a implementação com todos os métodos CRUD.

O que JpaRepository fornece automaticamente

MétodoSQL equivalente
save(entity)INSERT ou UPDATE (conforme o id)
findById(id)SELECT * FROM tabela WHERE id = ?
findAll()SELECT * FROM tabela
findAll(pageable)SELECT * FROM tabela LIMIT ? OFFSET ?
deleteById(id)DELETE FROM tabela WHERE id = ?
existsById(id)SELECT COUNT(*) FROM tabela WHERE id = ?
count()SELECT COUNT(*) FROM tabela

Tipos de query no Spring Data

1. Derived Query (nome do método vira a query)

public interface UsuarioRepository extends JpaRepository<Usuario, Long> {

    // Spring lê "findByEmail" e gera: SELECT * FROM usuarios WHERE email = ?
    Optional<Usuario> findByEmail(String email);
}

2. @Query com JPQL (linguagem de query do JPA — usa nome das classes Java, não tabelas SQL)

@Query("select c from Conteudo c where lower(c.genero) = lower(:genero)")
List<Conteudo> findByGeneroCaseInsensitive(@Param("genero") String genero);

// JPQL usa: nome da CLASSE Java (Conteudo) e nome do CAMPO Java (genero)
// SQL usa: nome da TABELA (conteudo) e nome da COLUNA (genero)

3. Paginação com Pageable

@Query("select c from Conteudo c order by c.relevancia desc")
Page<Conteudo> findTopByRelevancia(Pageable pageable);

// No Service: Pageable.ofSize(10) → retorna os 10 primeiros
// No Controller: @PageableDefault(size=10) Pageable pageable

DTOs — Data Transfer Objects

RequestDTO · ResponseDTO · Por que não expor a Entity diretamente

DTO (Data Transfer Object) É um objeto simples que carrega apenas os dados necessários para uma operação específica. Separa o que a API recebe/devolve (DTO) do que está salvo no banco (Entity). Isso é essencial para segurança, flexibilidade e controle sobre o que é exposto.

Por que não usar a Entity diretamente na API?

Sem DTO (problema)

  • A senha seria retornada no JSON
  • Campos internos (senhaHash, criadoEm) ficam expostos
  • Mudança no banco quebra a API
  • Não há validação específica por operação

Com DTO (solução)

  • RequestDTO: define o que o cliente pode enviar
  • ResponseDTO: define o que o cliente recebe
  • Senha nunca vai no ResponseDTO
  • Validações específicas por operação

Padrão Request/Response do projeto

// ENTRADA (o que o cliente envia para criar um usuário):
public class UsuarioRequestDTO {
    @NotBlank  String nome;
    @Email @NotBlank  String email;
    @NotBlank @Size(min = 8)  String senha;   // enviada pelo cliente
    @CpfCnpj  String cpfCnpj;
    @Past  LocalDate dataNascimento;
}

// SAÍDA (o que a API devolve):
public class UsuarioResponseDTO {
    Long id;
    String nome;
    String email;
    String cpfCnpj;
    LocalDate dataNascimento;
    String perfil;
    LocalDateTime criadoEm;
    // senha NÃO aparece aqui!
}

O papel do Mapper

// Mapper converte Entity ↔ DTO
@Component
public class UsuarioMapper {

    public Usuario toEntity(UsuarioRequestDTO dto) {
        return Usuario.builder()
            .nome(dto.getNome())
            .email(dto.getEmail())
            // senha NÃO vai aqui: é tratada no Service com BCrypt
            .build();
    }

    public UsuarioResponseDTO toResponseDTO(Usuario u) {
        return UsuarioResponseDTO.builder()
            .id(u.getId())
            .nome(u.getNome())
            .email(u.getEmail())
            // senhaHash NÃO vai para o cliente
            .build();
    }
}
Pergunta frequente em provas: "Qual a diferença entre Entity e DTO?" — Entity é mapeada para o banco de dados. DTO é usado apenas para transferir dados entre o cliente e a API, sem acoplamento com o banco.

Services — Regras de Negócio

@Service · @Transactional · EntityNotFoundException

Service É a camada onde ficam as regras de negócio da aplicação. O Controller apenas recebe a requisição e delega para o Service. O Service decide o que fazer: validar, buscar, salvar, lançar exceções, chamar outras classes.

Anotações importantes do Service

AnotaçãoO que faz
@ServiceRegistra a classe como bean do Spring, tornando-a injetável
@TransactionalAbre uma transação no banco. Se o método lançar exceção, faz rollback automático
@RequiredArgsConstructorLombok: gera construtor com todos os campos final, que o Spring usa para injeção
@Slf4jLombok: cria a variável log para registrar logs

Exemplo: UsuarioService — criação com regra de negócio

@Service
@RequiredArgsConstructor
@Slf4j
public class UsuarioService {

    private final UsuarioRepository usuarioRepository;
    private final UsuarioMapper usuarioMapper;
    private final BCryptPasswordEncoder passwordEncoder;

    @Transactional                                   // abre transação
    public UsuarioResponseDTO criar(UsuarioRequestDTO dto) {
        log.info("Criando usuário: {}", dto.getEmail());

        // REGRA DE NEGÓCIO: e-mail único
        usuarioRepository.findByEmail(dto.getEmail()).ifPresent(u -> {
            throw new DataIntegrityViolationException("Email já cadastrado");
        });

        Usuario usuario = usuarioMapper.toEntity(dto);

        // REGRA: senha deve ser armazenada com hash BCrypt
        usuario.setSenhaHash(passwordEncoder.encode(dto.getSenha()));

        Usuario salvo = usuarioRepository.save(usuario);
        return usuarioMapper.toResponseDTO(salvo);
    }

    public UsuarioResponseDTO buscarPorId(Long id) {
        // REGRA: lança exceção se não encontrado (tratada pelo GlobalExceptionHandler)
        Usuario usuario = usuarioRepository.findById(id)
            .orElseThrow(() -> new EntityNotFoundException("Usuário não encontrado: " + id));
        return usuarioMapper.toResponseDTO(usuario);
    }
}

Por que @Transactional é importante?

Sem @Transactional

  • Se salvar A e B e B falhar, A permanece salvo
  • Dados inconsistentes no banco
  • Difícil de reverter

Com @Transactional

  • Se qualquer operação falhar, tudo é desfeito (rollback)
  • Banco fica em estado consistente
  • Automático: não precisa de código de rollback
O @Transactional deve ficar nos métodos de escrita (criar, atualizar, deletar). Métodos de leitura (listar, buscar) geralmente não precisam.

Controllers — Endpoints REST

@RestController · HTTP Methods · ResponseEntity · Paginação

REST (Representational State Transfer) É um estilo arquitetural para APIs web. Cada recurso tem uma URL própria. As operações são feitas pelos verbos HTTP (GET, POST, PUT, DELETE). As respostas são em JSON. O status HTTP indica o resultado da operação.

Anotações dos Controllers

AnotaçãoO que faz
@RestControllerCombina @Controller + @ResponseBody. Todos os métodos retornam JSON automaticamente
@RequestMapping("/rota")Define o prefixo de URL para todos os métodos da classe
@GetMapping / @PostMappingMapeiam o método HTTP para o método Java
@PathVariableExtrai valor da URL: /usuarios/{id}
@RequestBodyExtrai o JSON do corpo da requisição e converte para DTO
@RequestParamExtrai parâmetro da query string: /conteudos/buscar?termo=action
@ValidAtiva a validação do DTO (Bean Validation)

Exemplo: UsuarioController completo

@RestController
@RequestMapping("/usuarios")
@RequiredArgsConstructor
public class UsuarioController {

    private final UsuarioService usuarioService;

    @PostMapping
    public ResponseEntity<UsuarioResponseDTO> criar(@Valid @RequestBody UsuarioRequestDTO dto) {
        UsuarioResponseDTO criado = usuarioService.criar(dto);
        // Cria o header Location: /usuarios/42
        URI location = ServletUriComponentsBuilder.fromCurrentRequest()
            .path("/{id}").buildAndExpand(criado.getId()).toUri();
        return ResponseEntity.created(location).body(criado);  // 201 Created
    }

    @GetMapping
    public ResponseEntity<Page<UsuarioResponseDTO>> listar(
            @PageableDefault(size = 20) Pageable pageable) {
        return ResponseEntity.ok(usuarioService.listar(pageable));  // 200 OK
    }

    @GetMapping("/{id}")
    public ResponseEntity<UsuarioResponseDTO> buscarPorId(@PathVariable Long id) {
        return ResponseEntity.ok(usuarioService.buscarPorId(id));
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> deletar(@PathVariable Long id) {
        usuarioService.deletar(id);
        return ResponseEntity.noContent().build();              // 204 No Content
    }
}

Bean Validation — Validação de Dados

@NotBlank · @Email · @Valid · MethodArgumentNotValidException

Bean Validation (jakarta.validation) É uma especificação Java para validar objetos através de anotações nos campos. Quando o Spring encontra @Valid em um parâmetro do controller, ele automaticamente valida o objeto antes de executar o método. Se a validação falhar, lança MethodArgumentNotValidException.

Todas as anotações de validação usadas no projeto

AnotaçãoRegraOnde é usada
@NotBlankNão pode ser nulo, vazio ou só espaçosnome, email, titulo, tipo, tokenizado
@NotNullNão pode ser nulo (aceita string vazia)usuarioId, principal
@EmailDeve ter formato válido de e-mail (com @)UsuarioRequestDTO.email
@PastData deve ser anterior a hojeUsuarioRequestDTO.dataNascimento
@Size(min=8)String deve ter no mínimo 8 caracteresUsuarioRequestDTO.senha
@Min(1888)Número deve ser maior ou igual a 1888ConteudoRequestDTO.ano
@Max(2100)Número deve ser menor ou igual a 2100ConteudoRequestDTO.ano
@PositiveNúmero deve ser positivo (maior que 0)ConteudoRequestDTO.duracaoMinutos
@DecimalMin("0.0")Decimal deve ser ≥ 0.0ConteudoRequestDTO.relevancia
@DecimalMax("10.0")Decimal deve ser ≤ 10.0ConteudoRequestDTO.relevancia
@CpfCnpjDeve ser CPF ou CNPJ válido (customizada)UsuarioRequestDTO.cpfCnpj

Como a validação funciona na prática

1. Cliente envia POST /usuarios com JSON inválido (e-mail sem @): { "nome": "João", "email": "joao-sem-arroba" } 2. Jackson deserializa para UsuarioRequestDTO 3. Spring detecta @Valid no parâmetro do Controller: public ResponseEntity criar(@Valid @RequestBody UsuarioRequestDTO dto) 4. Hibernate Validator verifica as anotações: @Email → "joao-sem-arroba" ✗ INVÁLIDO 5. Lança MethodArgumentNotValidException 6. GlobalExceptionHandler captura e retorna: HTTP 400 Bad Request { "status": 400, "message": "Dados inválidos na requisição" }
Ponto importante: As anotações de validação nos campos das Entities (como @NotBlank em Usuario.nome) são validadas pelo Hibernate antes de salvar no banco. As anotações nos DTOs (como @NotBlank em UsuarioRequestDTO.nome) são validadas pelo Bean Validation quando o @Valid está presente no controller.

Validação Customizada — @CpfCnpj

@Constraint · ConstraintValidator · Anotação própria

Validação Customizada Quando as anotações prontas do Bean Validation não atendem, podemos criar nossa própria anotação de validação. São necessárias 2 classes: (1) a anotação que define o contrato, e (2) o validador que implementa a lógica.

Passo 1: Criar a anotação @CpfCnpj

@Documented
@Constraint(validatedBy = CpfCnpjValidator.class) // vincula ao validador
@Target(ElementType.FIELD)                          // aplica em campos
@Retention(RetentionPolicy.RUNTIME)                 // disponível em tempo de execução
public @interface CpfCnpj {
    String message() default "CPF ou CNPJ inválido";  // mensagem de erro padrão
    Class<?>[] groups() default {};                    // obrigatório pela spec
    Class<? extends Payload>[] payload() default {}; // obrigatório pela spec
}

Passo 2: Implementar o validador

public class CpfCnpjValidator implements ConstraintValidator<CpfCnpj, String> {

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        if (value == null) return true;  // null é permitido (use @NotNull se quiser proibir)

        String digits = value.replaceAll("\\D", "");  // remove . - /

        if (digits.length() == 11) return isValidCpf(digits);
        if (digits.length() == 14) return true;  // tamanho válido para CNPJ
        return false;
    }

    private boolean isValidCpf(String cpf) {
        // Rejeita CPFs com todos os dígitos iguais (111.111.111-11)
        if (cpf.chars().distinct().count() == 1) return false;

        // Verifica primeiro dígito verificador
        int sum = 0;
        for (int i = 0; i < 9; i++) sum += (cpf.charAt(i) - '0') * (10 - i);
        int first = 11 - (sum % 11);
        if (first >= 10) first = 0;
        if (first != (cpf.charAt(9) - '0')) return false;

        // Verifica segundo dígito verificador
        sum = 0;
        for (int i = 0; i < 10; i++) sum += (cpf.charAt(i) - '0') * (11 - i);
        int second = 11 - (sum % 11);
        if (second >= 10) second = 0;
        return second == (cpf.charAt(10) - '0');
    }
}

Como é usado

public class UsuarioRequestDTO {
    @CpfCnpj           // usa nossa anotação customizada
    private String cpfCnpj;
}
O fluxo é: @CpfCnpj no campo → Spring detecta @Constraint(validatedBy=CpfCnpjValidator.class) → instancia o validador → chama isValid() → se retornar false, a validação falha com a mensagem definida.

Implementação do GlobalExceptionHandler

@Slf4j
@RestControllerAdvice                    // intercepta exceções de todos os controllers
public class GlobalExceptionHandler {

    @ExceptionHandler(EntityNotFoundException.class)
    public ResponseEntity<Map<String, Object>> handleEntityNotFound(
            EntityNotFoundException ex, HttpServletRequest request) {

        Map<String, Object> body = new LinkedHashMap<>();
        body.put("timestamp", LocalDateTime.now());
        body.put("status", 404);
        body.put("error", "Not Found");
        body.put("message", ex.getMessage());
        body.put("path", request.getRequestURI());

        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(body);
    }
}

API 1: ViaCEP com OpenFeign (cliente declarativo)

OpenFeign É um cliente HTTP declarativo: você define uma interface Java com anotações e o Spring cria a implementação automaticamente. Não precisa escrever código de conexão HTTP. 
// 1. Interface declarativa — Spring gera a implementação:
@FeignClient(name = "viaCepClient", url = "${viacep.url:https://viacep.com.br/ws}")
public interface ViaCepClient {
    @GetMapping("/{cep}/json/")

}
// URL final: https://viacep.com.br/ws/01310100/json/

// 2. DTO que deserializa a resposta JSON do ViaCEP:

    private String cep, logradouro, bairro, localidade, uf;
    @JsonProperty("erro")

// 3. Configuração da URL em application.properties:
viacep.url=https://viacep.com.br/ws

// 4. Uso no FuncionarioService:

funcionario.setLogradouro(endereco.getLogradouro());

API 2: BrasilAPI com RestTemplate (cliente imperativo)

RestTemplate É o cliente HTTP clássico do Spring. Você chama métodos explicitamente passando a URL e o tipo esperado de retorno. É mais verboso que o Feign, mas mais simples para casos pontuais. 
// 1. Bean RestTemplate declarado em AppConfig:
@Configuration
public class AppConfig {
    @Bean
    public RestTemplate restTemplate() { return new RestTemplate(); }
}

// 2. Service que consome a BrasilAPI:
@Service
public class BrasilApiService {
    private final RestTemplate restTemplate;

    public List<FeriadoResponse> listarFeriados(Integer ano) {
        String url = "https://brasilapi.com.br/api/feriados/v1/" + ano;
        FeriadoResponse[] feriados = restTemplate.getForObject(url, FeriadoResponse[].class);
        return Arrays.asList(feriados != null ? feriados : new FeriadoResponse[0]);
    }
}

// 3. DTO da resposta:
public class FeriadoResponse {

    private String name;   // "Confraternização Universal"

Correlation-ID e Logging

MDC · Filter · Rastreabilidade de Requisições

Correlation-ID É um identificador único (UUID) gerado para cada requisição HTTP. Ele é injetado em todos os logs daquela requisição, permitindo rastrear o fluxo completo de uma chamada nos logs, mesmo em sistemas com muitas requisições simultâneas.

Como está implementado: CorrelationIdFilter

@Component                              // registrado automaticamente pelo Spring
public class CorrelationIdFilter implements Filter {

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {

        String correlationId = UUID.randomUUID().toString();  // gera ID único
        MDC.put("correlationId", correlationId);             // injeta no contexto de log
        try {
            chain.doFilter(req, res);  // deixa a requisição continuar
        } finally {
            MDC.clear();              // limpa ao final (evita vazamento entre threads)
        }
    }
}

Configuração do padrão de log (application.properties)

# O %X{correlationId} injeta o valor do MDC em cada linha de log:
logging.pattern.console=%d{HH:mm:ss} [%X{correlationId}] %-5level %logger{36} - %msg%n

Como aparece nos logs

// Sem Correlation-ID — difícil rastrear:
14:30:01 INFO UsuarioService - Criando usuário: joao@email.com
14:30:01 INFO UsuarioService - Criando usuário: maria@email.com
14:30:01 INFO UsuarioService - Usuário criado com ID: 1
14:30:01 INFO UsuarioService - Usuário criado com ID: 2

// Com Correlation-ID — fácil rastrear qual log pertence a qual requisição:

14:30:01 [xyz-456-ghi] INFO UsuarioService - Criando usuário: maria@email.com
14:30:01 [abc-123-def] INFO UsuarioService - Usuário criado com ID: 1
14:30:01 [xyz-456-ghi] INFO UsuarioService - Usuário criado com ID: 2
MDC (Mapped Diagnostic Context) É um mapa de pares chave-valor mantido pelo framework de log (SLF4J/Logback) por thread. Qualquer valor colocado no MDC aparece automaticamente em todos os logs gerados por aquela thread, sem precisar passar o valor manualmente para cada método.

BCrypt — Hash de Senhas

spring-security-crypto · BCryptPasswordEncoder · Segurança

Hash de senha Senhas NUNCA devem ser armazenadas em texto puro no banco. BCrypt é um algoritmo de hash unidirecional: transforma a senha em uma string aleatória irreversível. Para verificar a senha, compara-se o hash, não a senha em texto puro.

Como está implementado

// 1. Bean declarado em AppConfig (sem ativar Spring Security completo):
@Configuration
public class AppConfig {
    @Bean
    public BCryptPasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

// 2. Uso no UsuarioService na criação:
usuario.setSenhaHash(passwordEncoder.encode(dto.getSenha()));
// "minha123" → "$2a$10$X9kGKjx8Qv2K3..."  (irreversível)

// 3. O ResponseDTO NÃO inclui senhaHash:
public class UsuarioResponseDTO {
    private Long id;
    private String nome;
    private String email;
    // senhaHash propositalmente omitida
}

Por que BCrypt é preferido?

CaracterísticaDetalhe
UnidirecionalImpossível reverter o hash para obter a senha original
Salt automáticoGera um salt aleatório para cada senha, evitando rainbow tables
Custo ajustávelO fator de custo pode ser aumentado conforme o hardware evolui
Dois hashes diferentesencode("123") chamado 2x gera resultados diferentes, mas ambos válidos
Nunca armazene senhas em texto puro. Mesmo que o banco seja comprometido, com BCrypt o atacante não consegue as senhas reais.

Perguntas e Respostas para a Prova

Questões objetivas e dissertativas mais prováveis

Bloco 1 — Conceitos Fundamentais

Q: O que é o Spring Boot e qual sua principal vantagem sobre o Spring Framework puro? Spring Boot é um framework que simplifica a criação de aplicações Spring com autoconfiguração, servidor embutido e starters. Sua principal vantagem é eliminar configurações manuais: com pouquíssimas linhas de código, a aplicação já está funcionando com Tomcat, JPA, Swagger etc. configurados automaticamente.
Q: Qual é a diferença entre @Component, @Service, @Repository e @Controller? Todas são especializações de @Component (registram beans no contexto Spring), mas com semântica específica: @Service indica lógica de negócio, @Repository indica acesso a dados e permite tradução de exceções JPA, @Controller/@RestController indica camada de apresentação HTTP.
Q: Para que serve a anotação @Transactional? Ela garante que todas as operações de banco de dados dentro do método ocorram como uma única transação atômica. Se qualquer operação falhar, o Spring faz rollback automático, mantendo o banco em estado consistente.

Bloco 2 — JPA e Persistência

Q: O que é JPQL e como difere do SQL? JPQL (Java Persistence Query Language) é a linguagem de consulta do JPA. Diferente do SQL que opera sobre tabelas e colunas, o JPQL opera sobre classes Java e seus campos. Ex: SQL: SELECT * FROM usuarios WHERE email = ? → JPQL: SELECT u FROM Usuario u WHERE u.email = ?.
Q: O que acontece com ddl-auto=update? O Hibernate cria tabelas que não existem e adiciona novas colunas às existentes. Porém, nunca remove colunas nem apaga dados. É seguro para desenvolvimento, mas em produção usa-se validate ou none.
Q: O que é @ManyToOne e @JoinColumn? @ManyToOne declara um relacionamento N:1 entre entidades. @JoinColumn define o nome da coluna de chave estrangeira no banco. Ex: em Assinatura, @ManyToOne + @JoinColumn(name="usuario_id") cria a coluna usuario_id na tabela assinatura apontando para a tabela usuarios.

Bloco 3 — REST e HTTP

Q: Quais os verbos HTTP usados na API e seus significados? GET (buscar/listar), POST (criar → retorna 201 Created), PUT (atualizar completamente → retorna 200 OK), DELETE (remover → retorna 204 No Content).
Q: Para que serve o ResponseEntity? Permite controlar a resposta HTTP completa: status code, headers e body. Ex: ResponseEntity.created(uri).body(dto) retorna 201 com o header Location preenchido.
Q: Qual a diferença entre @PathVariable e @RequestParam? @PathVariable extrai um segmento da URL: /usuarios/{id} → @PathVariable Long id. @RequestParam extrai da query string: /conteudos/buscar?termo=acao → @RequestParam String termo.

Bloco 4 — Validação e Exceções

Q: Como funciona o @Valid nos controllers? Quando @Valid é colocado antes de um @RequestBody, o Spring valida automaticamente o objeto recebido usando as anotações do Bean Validation (@NotBlank, @Email etc.). Se alguma validação falhar, lança MethodArgumentNotValidException, capturada pelo GlobalExceptionHandler que retorna 400.
Q: O que é @RestControllerAdvice e por que é importante? É uma classe que intercepta exceções lançadas por qualquer controller. Centraliza o tratamento de erros: em vez de try/catch em cada método, todas as exceções são tratadas em um único lugar, garantindo respostas padronizadas e consistentes.
Q: Como criar uma anotação de validação customizada? São necessários 2 elementos: (1) uma anotação com @Constraint(validatedBy=MinhaClasse.class) e os atributos obrigatórios message(), groups() e payload(), e (2) uma classe que implementa ConstraintValidator<MinhaAnotacao, TipoDoValor> com o método isValid().

Bloco 5 — Integrações e Configurações

Q: Qual a diferença entre OpenFeign e RestTemplate? OpenFeign é declarativo: você define uma interface e o Spring cria a implementação. RestTemplate é imperativo: você chama métodos explicitamente passando a URL. Feign é mais moderno, menos verboso e ideal para múltiplos endpoints. RestTemplate é mais simples para casos pontuais.
Q: Por que usar BCrypt para senhas e não MD5 ou SHA-1? BCrypt é lento por design (fator de custo), gera um salt único para cada hash tornando inviável rainbow tables, e é unidirecional. MD5 e SHA-1 são rápidos demais (facilitam ataques de força bruta) e não incluem salt automático.
Q: Para que serve o Correlation-ID? Para rastrear o fluxo completo de uma requisição nos logs. Um UUID é gerado no filtro, injetado no MDC (Mapped Diagnostic Context) e aparece em todas as linhas de log daquela requisição. Facilita a depuração quando várias requisições ocorrem simultaneamente.
Q: O que é DTO e por que não expor diretamente a Entity na API? DTO (Data Transfer Object) é um objeto que carrega apenas os dados necessários para uma operação. Expor a Entity diretamente criaria acoplamento entre o banco e a API, poderia vazar campos sensíveis (senhaHash) e tornaria impossível ter formatos diferentes para entrada e saída.
Q: O que o Lombok gera com @Data? Getters e setters para todos os campos, equals() e hashCode() baseados em todos os campos, toString() e o construtor padrão (sem parâmetros, caso não haja @NoArgsConstructor). Tudo gerado em tempo de compilação, sem custo em runtime.
